# A file you bound to a case offers that case again when you open it, after a restart too, and binds it with your click

- **Issue:** #107, AS8
- **Upstream doc it would have touched:** `ROADMAP.md`
- **Not verified:** the offer's line and its buttons on a real screen (the tests check the offer the line reads and the functions its buttons call, headlessly); Windows paths, which the tests don't run on.

Until now the binding lived only in the window's memory, keyed by the per-process document id, so after a restart recall and case notes silently stopped applying until the person bound the document again.

The person's bind is now also kept for the document's file in `assistant-cases/bindings.json`, beside the walls: `{"version":1,"files":[{"path":…,"wall":…,"case":…}]}`, keyed by the file's canonical path. Nothing goes into the document, whose `custom.xml` anyone can write. The format is closed like `case.json`: `deny_unknown_fields`, one version, at most 200 files, paths of at most 4 KiB as written, and 1 MiB in all (a test fills every limit with paths whose backslashes double when escaped). A file that breaks any of that binds nothing, and the person's next bind or unbind moves it aside as `bindings.json.damaged` before writing, as `assistant-memory.json` is. Writes take `bindings.lock` and replace the file in a rename through `atomic.rs`, as the cases do.

Only the person writes it: `assist.memory.case.bind`, `.new` and `.unbind` keep or forget the shown document's path after the in-memory binding changes, inside the same person-only commands as before, so no guard changed. Delete forgets every file bound to the case between the rename to trash and the folder's removal, and the sweep that finishes a delete a crash interrupted does the same before removing the trash, so a crash at either point leaves nothing bound to a deleted case. Deleting only a case's record (`log/`) goes through the same trash as `<case id>-log`, which names no binding, so the file stays bound, and a case deleted with its record in it still forgets its files; a test covers both and the sweep of a record's interrupted delete. A binding whose case is gone some other way is dropped when its file is opened, without waiting for another window's lock.

The window looks a document's file up once, the first frame it is shown. Once per document is the rule that keeps a copy from inheriting: Save As keeps the document's id, so a copy saved under a new name is never looked up, and its path has no binding for the next time. The same rule means a document bound before its first save is bound only in this window, and the docs say to bind it again once it has a file.

The case is offered, not bound: "When you last had this file open, it was bound to <case>" with **Bind again** and **Not now**, above the conversation and on Details › Case while the document is unbound. Bind again runs `assist.memory.case.bind`, the person-only command a click in the case list runs; Not now hides the offer while the document is open, and the next open offers it again. Nothing recalls from the case until the click. A path doesn't say which document is there, and a bound case's facts, balance, plan and notes go to the model with every turn, so binding by the path alone would send the first client's case to the model while it works on another client's document saved over the path. The first version of this change bound the file again by itself; a review found that, and a second version kept some of the document's block ids and bound only when the opened document still held one. Codex review on #135 found that this doesn't establish the document either: documents made from the same template keep the template's block ids (`file.newFromTemplate` keeps the ids a file has), and a save in Word drops `wc:blockId` and keeps only the 31-bit `w14:paraId`, so a document edited in Word lost its binding. The owner chose the click over a binding that comes back by itself. `a_files_case_is_offered_after_a_restart_and_binds_only_with_the_persons_click` fails if the file binds by itself.
